## Що було на вході

Локальна розшифровка, читання Git і робота Flux підтверджують різні шари; жоден сигнал сам не доводить, що потрібний Pod має Secret, тож не святкуй завчасно, бляха.

### Дано

Кластер на одному k3s-вузлі має синхронізуватися з Git через Flux. Kubernetes Secret потрібно тримати в Git, редагувати локально лише на короткий момент у відкритому вигляді і довірити розшифрування самому Flux під час reconcile — без ручного `kubectl apply` для секретів.

### Що сталося

Я обрав SOPS із провайдером age. Шифрування прив’язане до публічного recipient, приватна identity існує лише поза Git, а файл лишається звичайним Kubernetes-маніфестом із зашифрованими значеннями. Рішення здавалося завершеним на кожному проміжному кроці: `kubectl` відповідав, Flux читав репозиторій, локальний decrypt проходив. Жоден із цих сигналів окремо не підтверджував, що тестовий Secret насправді дістався Pod.

Оце й є зручний самообман: три успішні перевірки сусідніх шарів склеїли в одну гарантію для Pod, хоча жодна не доходить до споживача. Це не «майже готово», а пропущене наскрізне підтвердження. І без резервної копії identity додає окремий ризик: утратити ключ — і старі шифротексти вже не відновити, бляха.

### Як розбиралися

Кожен шар перевіряли окремо: kube-context і адресу API server — окремо від стану нод; стан `GitRepository` — окремо від застосованої ревізії `Kustomization`; staged-файл перед commit — окремо від історії Git; namespace і `secretRef` `Kustomization` — окремо від факту, що `sops` локально розшифровує той самий файл.

### Що встановили

SOPS + age шифрує дані в Git; розшифровує їх не термінал автора, а окремий Secret, який читає `kustomize-controller` у просторі імен свого `Kustomization`, а не в просторі імен застосунку. Далі — практичний шлях від чистого Linux-хоста до Pod, який підтверджує, що прочитав очікуване тестове значення.

## Чому age, а не GPG чи sealed-secrets

Для одновузлового k3s із Flux важливо, скільки додаткових рухомих частин вимагає сам механізм шифрування. GPG працює з web of trust, ключовими серверами й agent-процесом — зайва складність для одного recipient. Sealed-secrets вирішує ту саму задачу, але вимагає окремого контролера в кластері зі своїм ключем, який теж треба десь резервувати; це рухома частина додатково до самого Flux. Vault розв’язує набагато більше задач, але для цього потрібен запущений сервер і автентифікація до нього — зайва залежність для єдиної мети «зашифрований Secret у Git».

Age — пара асиметричних ключів без інфраструктури: один файл-identity, один recipient-рядок. SOPS підтримує age як рівноправного провайдера поруч із KMS і PGP, а Flux розшифровує SOPS-файли без стороннього контролера, якщо `kustomize-controller` отримав потрібний ключ. Для одного вузла й одного репозиторію це найменша кількість частин, здатних зламатися.

## Де лежить identity і що не входить у Git

У Git потрапляє лише публічний recipient — рядок, який SOPS записує у зашифрований файл і який нічого не розкриває без приватної половини. Приватна age identity живе виключно поза репозиторієм: на робочій станції, у файлі з обмеженими правами. Той самий файл дає значення для Secret `sops-age`, який пізніше читає `kustomize-controller` у кластері.

Якщо цей файл зникне без резервної копії, зашифровані цим recipient-ом Secret не розшифровуються — відновлення тут не означає «розшифрувати назад», воно означає «згенерувати нову пару ключів і перешифрувати все, що було зашифроване для старої». Тому перед тим, як ця identity піде в продуктивне використання, її копія має опинитися в менеджері секретів команди — не в Git, не на спільному диску, не в тому самому бекапі, що й решта workstation.
