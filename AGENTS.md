# ops.notes — інструкції

## Робочий процес

- Відповідай українською, стисло і практично; для англомовного запиту коротко наведи природніше формулювання. Зберігай чинний дизайн і голос автора, якщо не доручено інше.
- Сайт статичний, без CMS, бази й залежностей для збірки; пошук і фільтри працюють у браузері. `tools/sites/` — інструменти й шаблони Sites, а не вихідний код блогу.
- `content/<slug>.md` — стаття та metadata; `practical/<slug>.md` обов’язковий; `examples/<slug>.md` необов’язковий і додається до практичного блоку. Назва файла визначає URL.
- `scripts/build.mjs` генерує відстежувані `dist/index.html`, `dist/about.html` та `dist/articles/*.html`; не редагуй їх вручну. `dist/style.css` і `dist/app.js` — першоджерела. `work/` та `outputs/` — ігноровані локальні артефакти.
- Збірка не очищує `dist/articles/`: після видалення чи перейменування статті перевір старі HTML, щоб не залишити копію, особливо після анонімізації. Не змінюй опублікований slug без перенаправлення; наявні redirects генеруються в `scripts/build.mjs`.
- Metadata однорядкові: `title`, `category`, `summary`, `order`, `excuse`, `verdict`, `consequence`, `selfroast`; вибирай унікальний наступний `order` за файлами. Для кейсу з практики додавай `kind: history` та анонімізоване `evidence` з межами підтвердження; для ілюстративного розбору не додавай `kind: history`.
- Власний Markdown renderer підтримує абзаци, `##`, `###`, inline code, fenced code blocks і HTTP/HTTPS-посилання. Інший синтаксис перевіряй у `scripts/build.mjs`. Зміст будується з `##`; anchor `practical` задається заголовком, що починається з `Тепер корисне:`. Виділена стаття на головній задана у build script явно.

## Редакція та безпека

- Пиши українською голосом досвідченого DevOps-інженера, який прямо говорить про власні прорахунки. Для реального кейсу використовуй першу особу там, де рішення чи дія справді належали авторові. Без матюків, самоприниження й підколів колег. Ілюстративний матеріал позначай як «Технічний розбір». У видимому тексті не використовуй слово «байка» та його форми або «Навчальний сценарій».
- Починай із ситуації: контекст, компоненти й симптом. Розбери, на чому трималося рішення, чому воно здавалося розумним і якої перевірки бракувало. Якщо сигнал був слабким, назви, що саме він підтверджував і який висновок автор зробив завчасно. Далі поясни механізм, підтверджений наслідок і практичні дії. Якщо рішення було виправданим за наявних тоді даних, прямо це скажи.
- Додавай самоіронію там, де видно розрив між моєю впевненістю і тим, що я реально перевірив. Ціль для жарту — поспіх, зайве ускладнення, пропущена перевірка чи передчасне «готово». Наприклад: «Побачив `Running` і подумки закрив інцидент. Запит до сервісу я тоді так і не зробив». Використовуй таку репліку лише за відповідних фактів. У командах, критеріях перевірки й rollback тримай тон прямим.
- У metadata `excuse` передає правдоподібне виправдання автора на той момент, `verdict` дає прямий технічний висновок, `consequence` називає підтверджений наслідок або явно позначений ризик, а `selfroast` стисло підколює конкретне рішення чи припущення від першої особи. Не вигадуй промахів заради жарту. В ілюстративному розборі прив’язуй самоіронію до спокуси зробити поспішний висновок, без вигаданого інциденту з біографії автора.
- Не вигадуй логи, виміри, виконані команди чи успішне виправлення. Позначай гіпотетичну діагностику й межі доказів. Саркастичну репліку подавай як авторський коментар. Цитуй учасника лише за наявності підтвердженої цитати.
- Історії користувача анонімізуй: прибирай персональні дані, адреси, домени, ідентифікатори, точні дати, впізнавані шляхи й прив’язані до інсталяції назви та логи. Зберігай необхідні назви технологій. Використовуй placeholders на кшталт `<NAMESPACE>` і `<HOST_DATA_DIRECTORY>`. Ніколи не копіюй секрети чи credentials. Анонімізація поточного сайту не очищує Git-історію або версії Sites.
- Діагностику починай із read-only перевірок. Вказуй середовище, передумови, потрібні права, очікувані ознаки у виводі й межі кожної перевірки. Приклади виводу позначай як приклади. Підтверджуй версії та наявність контролерів, CSI чи metrics API. Змінні факти звіряй з офіційною документацією.
- Для фіксу показуй окремо було → стало → перевірка. Позначай часткові конфіги та вказуй їхній шлях. Зберігай решту наявних полів. Пояснюй, від чого залежать числові значення. Якщо зміна загрожує простоєм, втратою доступу чи даних, опиши передумови, ризики й спосіб повернення без гарантії відновлення даних. Видалення PVC/PV, очищення volumes, рекурсивний `chmod`/`chown` і перезапуск пропонуй лише за підтвердженої потреби. У GitOps змінюй декларативне джерело. Секрети отримуй через secret management і не передавай їх у відкритих CLI-аргументах.


## Перевірка

- З кореня: `node scripts/build.mjs`. Збірка перевіряє обов’язкові metadata, наявність practical-файлів і закриття code fences, але не перевіряє всі посилання чи унікальність `order`.
- Перед публікацією перевір внутрішні посилання, anchors, практичні блоки, анонімізацію та відсутність секретів. Для змін JavaScript — `node --check <файл>`; нові Bash-блоки перевіряй `bash -n`, YAML/JSON — відповідним parser. Це не доводить працездатності команд чи прийнятності маніфесту кластером; не запускай приклади на production заради перевірки статті.
- Після змін layout або renderer перевір сторінку в браузері: навігацію, читабельність, mobile layout і довгі code blocks.

## Публікація

- Для змін сайту використовуй актуальну навичку Sites і її workflow; локальна копія: `tools/sites/skills/sites/SKILL.md`. Повторно використовуй `project_id` з `.openai/hosting.json`, не створюй новий Site і не змінюй аудиторію чи приватний доступ без явного запиту. Публікуй синхронізований source state та відповідний archive; credentials передавай підтримуваним workflow через stdin, не записуй у файли, shell-аргументи чи повідомлення.
- Після доручених змін сайту публікуй оновлення, якщо не попросили local-only або save-only; зміна лише документації репозиторію деплою не потребує. Перевір terminal status і повідомляй точний URL, повернутий Sites; не заявляй про успіх без перевірки.
- `.gitea/workflows/deploy.yml` описує **ручний** `workflow_dispatch`: збірку, SSH-деплой в окреме середовище та HTTP-перевірку з runner. Git push не запускає його автоматично; наявність workflow не доводить доступності runner чи успішного деплою. Не запускай його замість Sites без доручення.
- Cloudflare Pages — погоджений майбутній напрям, не підтверджений як чинний deploy. Зберігай переносимий статичний `dist/`; майбутні налаштування: root репозиторію, build `node scripts/build.mjs`, output `dist`, зафіксована версія Node.js. Перед міграцією перевір прямі URL, `.html`/extensionless, anchors, redirects і 404. Не змінюй DNS, доступ або Sites без явного доручення; приватність між хостингами не переноситься автоматично.
