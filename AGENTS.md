# ops.notes — правила роботи з проєктом

## Мова та взаємодія

- Відповідай українською, коротко й практично. Спочатку результат, потім суттєві пояснення.
- Якщо запит англійською, коротко наведи природніше формулювання й відповідай українською.
- Виконуй погоджені зміни до завершення. Не проси повторного дозволу на вже доручену роботу.
- Перед зміною прочитай актуальні файли. Не перезаписуй сторонні чи незакомічені зміни.
- Не оголошуй зміну застосованою або публікацію успішною без відповідного результату перевірки.

## Призначення й характер блогу

Український технічний блог про DevOps, інфраструктуру та розбір помилок. Він має бути корисним читачеві, який не бачив попередніх обговорень.

- Зберігай чинний дизайн і голос автора, якщо користувач не доручив змінити їх.
- Голос — досвідчений інженер із помірним сарказмом і самоіронією. Автор розуміє механізми, але перевіряє власні припущення.
- Іронія стосується поспіху, звичок і надмірної впевненості. Не зображай автора безпорадним або некомпетентним.
- Не принижуй junior чи інших людей. Коментуй рішення, конфігурацію й наслідки.
- Без матюків, агресивного повчання та жарту в кожному абзаці.
- Приклад потрібної інтонації: «Знайомий модуль читається швидше. Іноді надто швидко. Тому операції заміни я переглядаю окремо».
- Не використовуй у видимих текстах слово «байка» та його форми, а також формулювання «Навчальний сценарій».
- Починай із самої ситуації. Для ілюстративного матеріалу достатньо нейтральної позначки «Технічний розбір» і короткого пояснення його природи.

## Структура кожної статті

Читач має послідовно зрозуміти:

1. **Дано:** що працювало, де, які компоненти та залежності потрібні для розуміння.
2. **Що сталося:** спостережувана проблема або питання до планованої зміни.
3. **Як розбиралися:** які дані перевірили, як вони підтвердили або відкинули припущення.
4. **Що встановили:** висновок і межі доказів, включно з невідомим результатом виправлення.
5. **Причина:** технічний механізм, пояснений послідовно й без зайвого жаргону.
6. **Практика:** команди, конфігурація, фікс, перевірка та, де потрібно, повернення.

- Поясни незнайомий компонент при першій появі: для чого він потрібен у цій історії.
- Спочатку контекст, потім висновок і самоіронія. Не починай із жарту, який зрозумілий лише учасникам чату.
- Не дублюй вступ у наступному розділі. Зв’язуй абзаци причиною та наслідком.
- Не вигадуй логів, аварій, вимірів, виконаних команд або успішного відновлення.
- Для ілюстративного розбору описуй, як перевіряти гіпотезу; не подавай змодельовану діагностику як реальну подію.
- Саркастична репліка автора — редакційний прийом, а не дослівна цитата реального учасника.

## Анонімізація

- Матеріали з історій користувача публікуй як анонімізовані кейси з практики.
- Прибирай персональні дані, імена користувачів, реальні адреси, домени, назви кластерів і вузлів, ідентифікатори, точні дати та впізнавані шляхи.
- Назви конкретних сервісів і дослівні логи узагальнюй, якщо вони прив’язують історію до інсталяції користувача. Стандартні назви технологій зберігай, коли без них втрачається технічна суть.
- Використовуй явні placeholders: `<NAMESPACE>`, `<POD_NAME>`, `<IMAGE_REFERENCE>`, `<HOST_DATA_DIRECTORY>`.
- Не копіюй секрети, паролі, токени, приватні ключі, вміст Kubernetes Secret або конфігурації з credentials.
- Зберігай межі підтвердження: встановлений дефект не дорівнює доведеному успіху виправлення. Історичний стан не подавай як поточний.
- Анонімізація поточної публікації не видаляє попередні Git-коміти чи збережені версії Sites. Не стверджуй протилежного.

## Технічна частина та snippets

- Починай діагностику з read-only перевірок. Називай середовище, prerequisites і потрібні права.
- Не припускай версії Kubernetes, Docker, Terraform, установлені контролери, CSI-драйвери чи наявність metrics API.
- Для змінних технічних фактів перевіряй актуальну офіційну документацію; додавай доречні посилання до статті.
- Для кожної команди поясни, що шукати у виводі та чого її успіх не доводить.
- Приклади виводу позначай як приклади. Не змішуй їх із зафіксованими доказами кейсу.
- Де є конкретний фікс, показуй **було → стало → перевірка** в окремих code blocks.
- Для часткового YAML/JSON/TOML/HCL називай файл або шлях у структурі, куди належить фрагмент. Не видавай уривок за повний production manifest.
- Зберігай наявні probes, ресурси, securityContext, мережі та інші поля при демонстрації вузької правки.
- Числові приклади ресурсів, таймаутів і портів не подавай як універсальні рекомендації.
- Не пропонуй видалення PVC/PV, очищення volumes, рекурсивний chmod/chown або перезапуск як універсальний спосіб ремонту.
- Для операції з простоєм, доступом або даними поясни передумови, ризик і повернення. Не обіцяй, що повернення конфігурації відновить змінені дані.
- Для GitOps змінюй декларативне джерело. Не додавай паралельний ручний apply без урахування контролера.
- Зберігай анонімізацію в snippets. Секрети отримуються через прийнятий secret-management процес, а не через відкритий CLI аргумент.

## Структура репозиторію

Сайт статичний, без CMS і бази даних. Пошук і фільтри працюють у браузері.

- `content/<slug>.md` — основний текст і metadata.
- `practical/<slug>.md` — обов’язковий однойменний практичний блок.
- `examples/<slug>.md` — необов’язкові конфігурації до/після та фікси.
- `scripts/build.mjs` — читання джерел, генерація HTML, навігації та переліків.
- `dist/index.html`, `dist/about.html`, `dist/articles/` — згенеровані сторінки; не редагуй їх вручну.
- `dist/style.css` — чинне оформлення; це першоджерело, його можна редагувати.
- `dist/app.js` — чинна клієнтська логіка; це першоджерело, його можна редагувати.
- `.openai/hosting.json` — прив’язка до наявного Sites та параметри hosting.
- `work/`, `outputs/` — локальні архіви, проміжні матеріали та скриншоти; не додавай їх до вихідного коду сайту. Зараз вони виключені через `.git/info/exclude`.

Підтримка Markdown обмежена власним renderer. Використовуй абзаци, `##`, `###`, inline code, fenced code blocks і HTTP/HTTPS-посилання. Перед додаванням таблиць, списків, HTML або іншого синтаксису перевір підтримку в `scripts/build.mjs`.

Metadata мають бути однорядковими. Обов’язкові поля:

```yaml
---
title: Назва статті
category: Kubernetes
summary: Короткий зрозумілий опис
order: <NEXT_ORDER>
excuse: Умовне припущення, яке перевіряємо
verdict: Технічний висновок
consequence: Можливий наслідок
selfroast: Коротка стримана самоіронічна примітка
---
```

- Для кейсу з зафіксованого досвіду додавай `kind: history` та `evidence:` з анонімізованими фактами й межами підтвердження.
- Для ілюстративного розбору не додавай `kind: history`.
- `order` — унікальне число; визначай наступне за актуальними файлами, не використовуй застарілу кількість статей.
- Однаковий slug потрібен у трьох каталогах. Назва файла визначає URL.
- Не змінюй опублікований slug без перенаправлення. Старий текст не повинен лишатися доступним як копія після анонімізації.
- Нова стаття автоматично потрапляє до переліку й категорій після збірки. Виділений матеріал на головній зараз заданий окремо в build script; не припускай автоматичного вибору.

## Збірка та перевірка

З кореня репозиторію:

```bash
node scripts/build.mjs
```

Перед публікацією:

- Перевір збірку, внутрішні посилання, anchors і наявність практичних блоків.
- Для змін JavaScript виконай доречний `node --check`.
- Нові Bash-блоки перевіряй через `bash -n`, YAML/JSON — відповідним parser.
- Структурна перевірка не доводить прийнятність маніфесту кластером або успішність команди на сервері. Не запускай приклади на production лише заради перевірки статті.
- Якщо змінюється layout або renderer, перевір представницьку сторінку в браузері: читабельність, навігацію, mobile layout та довгі code blocks без переповнення всієї сторінки.
- Повторно перевір анонімізацію, відсутність секретів і небажаних редакційних формулювань.

## Sites і публікація

- Для роботи із сайтом використовуй актуальну навичку Sites та її workflow.
- Повторно використовуй `project_id` із `.openai/hosting.json`. Не створюй новий Site для редагування цього блогу.
- Зберігай приватний доступ та поточну аудиторію, поки користувач явно не попросить іншого.
- Після доручених змін самого сайту публікуй оновлення, якщо користувач не попросив local-only або save-only. Для зміни лише документації репозиторію deploy не потрібний.
- Публікуй точний синхронізований source state та відповідний йому deployment archive.
- Credentials передавай підтримуваним workflow через stdin; не записуй токени до файлів, аргументів shell або повідомлень.
- Локальна збірка та звичайний Git push самі по собі зараз не запускають автоматичний deploy. Не стверджуй, що CI/CD налаштований.
- Перевір terminal status публікації. У відповіді використовуй точний URL, повернутий Sites; не набирай hostname з пам’яті.
- У фінальному повідомленні коротко зазнач, що змінив, що перевірив і що лишилося неперевіреним.

## Цільовий хостинг: Cloudflare Pages

- Погоджений напрям — надалі розгортати статичний сайт у Cloudflare Pages. Міграція та автоматичний deploy ще не налаштовані; Sites наразі залишається чинною публікацією.
- Зберігай переносимість: результат збірки — звичайні HTML/CSS/JS у `dist/`. Не додавай залежності від Sites runtime, серверної бази, авторизації чи API без явної потреби користувача.
- Для майбутньої Git-збірки Pages: root directory — корінь репозиторію, build command — `node scripts/build.mjs`, build output directory — `dist`.
- Node.js потрібен під час збірки; для обслуговування згенерованих сторінок серверний Node.js не потрібний. Версію build runtime слід зафіксувати під час налаштування CI.
- До публікації в Pages перевір пряме відкриття статей, поведінку `.html`/extensionless URL, anchors, старі перенаправлення, 404 і відсутність залежності від домену Sites.
- Не завантажуй на хостинг `.git/`, `.openai/`, `content/`, `practical/`, `examples/`, `work/` та `outputs/` як сайт: deployment artifact — лише вміст `dist/`.
- Аудиторія й доступ налаштовуються для нового хостингу окремо. Приватність Sites автоматично не переноситься до Pages. Не змінюй доступ чи DNS і не вимикай Sites до явного доручення на міграцію.
- Налаштування build command та output directory: https://developers.cloudflare.com/pages/configuration/build-configuration/
