## Тепер корисне: прочитай саме той plan

Приклад для вже ініціалізованого Terraform checkout із правильним backend. Планування читає реальні ресурси через провайдера; спочатку перевір обліковий запис і workspace. Plan-файл може містити секрети — не публікуй його й не додавай у Git.

### 1. Збережи план із контрольованими правами

```bash
terraform version
terraform workspace show
terraform validate
umask 077
terraform plan -out=review.tfplan
```

`validate` перевіряє конфігурацію, а не безпечність інфраструктурної зміни. Plan не виконує звичайне застосування змін, але потребує доступу до backend і provider API; custom data sources можуть мати власну поведінку.

### 2. Знайди видалення та заміни

За наявності jq виведи лише адреси й типи дій, а не повний JSON із чутливими значеннями:

```bash
terraform show -json review.tfplan | jq -r '
  .resource_changes[]?
  | select(.change.actions | index("delete"))
  | [.address, (.change.actions | join(" -> "))]
  | @tsv'
```

`delete` разом із `create` означає заміну; порядок залежить від плану. Порожній список каже лише, що цей фільтр не знайшов видалень. Він не перевіряє вартість, доступність, політики доступу або зміни поза цим списком.

### 3. До застосування

Переглянь повний plan у захищеній сесії. Для кожної заміни stateful-ресурсу з’ясуй долю даних і резервної копії. Рев’ю має стосуватися того самого saved plan; після перепланування потрібен новий перегляд.

Повернення старого `.tf` не скасовує видалення ресурсу чи записані дані. Якщо операція руйнує сховище, потрібна перевірена процедура відновлення до apply. Застосування навмисно не включене в цей діагностичний блок.
