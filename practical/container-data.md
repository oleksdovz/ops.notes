## Тепер корисне: зістав дані з mounts

Команди для Docker Engine; підстав ім’я конкретного контейнера. Вони читають метадані й не копіюють дані.

### 1. Звідки береться каталог у контейнері

```bash
export CONTAINER_NAME='<CONTAINER_NAME>'
docker inspect "$CONTAINER_NAME" --format \
  '{{range .Mounts}}{{printf "%s\t%s\t%s\tRW=%t\n" .Type .Source .Destination .RW}}{{end}}'
```

У кожному рядку: тип, source, destination та доступність запису. Порівняй destination з фактичним каталогом даних застосунку. Volume на `/cache` нічого не доводить щодо бази на іншому шляху.

Порожній список означає, що цих mounts немає. Застосунок усе одно може використовувати віддалену базу — це треба перевірити в його конфігурації, не публікуючи секрети.

### 2. Який саме образ і контейнер працюють

```bash
docker inspect "$CONTAINER_NAME" --format \
  'ImageID={{.Image}} Status={{.State.Status}} Restarts={{.RestartCount}}'
```

Image ID точніший за рухомий tag для ідентифікації поточного артефакту. `running` не доводить цілісність даних.

### 3. Перед заміною

Для СУБД зроби резервну копію підтримуваним нею способом. Копія каталогу активної бази без узгодження може бути непридатною. Перевір відновлення окремо, потім замінюй контейнер зі збереженим правильним mount.

Після заміни перевір той самий mount та наявність очікуваного запису через застосунок. Старий image tag повертає код, а не відновлює дані. Якщо нова версія зробила несумісну міграцію, rollback потребує окремого плану для схеми й даних.
